# Decision Log

Tracks *why* a call was made, not *what* was added (see `CHANGELOG.md` for that). One dated entry per meaningful decision. Newest at bottom.

## 2026-08-10

**Project title finalized as "Broadsheet & Rapier".**
"The Hollow Atlas" was an earlier working title, replaced. Engine identity finalized as "Thornwall" (not "thornwall-engine").

**Princess Trainer added as a UI/UX & interaction-mechanics inspiration, kept separate from narrative inspirations.**
It's a game, not a book, and has no bearing on tone, dialogue, or lore — only on interaction structure (stat-driven menus, time-slot scheduling, discrete location transitions, modal overlays). Placed in its own section of `narrative-inspirations.md` rather than merged into the Section 1/2 priority hierarchy, to avoid it leaking into narrative tone generation.

**Actor faction affiliation modeled as `factionIds: string[]` rather than a single `factionId`.**
An Actor can plausibly belong to more than one faction or have shifting allegiances; a single optional field couldn't represent that.

**District/POI given optional `controllingFactionId` and `factionInfluence` fields.**
Needed for locations to plausibly be contested or influenced by multiple factions rather than only cleanly owned or neutral.

**Territory deferred — no schema, no content, no reference field on Settlement.**
Not needed until macro-world/regional travel is actually implemented; adding it now would be unused scaffolding.

**`COMMAND_NEXT_DAY` made internal-only.**
It's a derived consequence of `COMMAND_ADVANCE_SHIFT` rolling past `NIGHT`, not an independent player action. Exposing it as a dispatchable UI command would let it be triggered out of sequence.

**`importSave` validates against `PlayerStateSchema` before writing to state, but without version migration logic.**
Protects against corrupted or hand-edited save files causing a crash. Full migration handling deferred until the state shape is stable enough that migrations are actually needed.

**Tailwind CSS v4 used instead of v3, changing the original setup plan.**
`npx tailwindcss init -p` no longer works in v4 — the CLI/init flow was removed upstream. v4 integrates via the `@tailwindcss/vite` plugin directly, no `postcss.config.js` or `tailwind.config.js`. Chosen over pinning to v3 because v4 is the current supported line going forward.

**`docs/system-rules.md` split into `docs/game-design-spec.md` (engine-agnostic) and `docs/web-implementation.md` (React/TS/Zustand-specific).**
The project may migrate off web technology (e.g. to Godot) in the future. Mixing domain rules (world clock, currency, content model) with implementation details (TypeScript interfaces, Zustand persistence, Tailwind classes) in one file meant a future migration would require manually untangling which parts still apply. Splitting means `game-design-spec.md` should survive a migration unchanged, and `web-implementation.md` is the only file that needs full replacement.

**Execution plan scoped explicitly as "Phase 0 — Technical Scaffold".**
The original plan covered engine types, schemas, store, starter content, tests, and UI shell — but no actual gameplay mechanics (minigame resolution, reputation effects, economy balance). Left unscoped, an implementer would have had to invent those to make anything "playable." Scaffold is now bounded to proving the architecture with inert content; gameplay mechanics require their own spec before implementation continues past it.

**`COMMAND_NEXT_DAY`'s internal-only status enforced structurally, not just by convention.**
The earlier decision (above) said it shouldn't be exposed as a UI action, but nothing stopped code from dispatching it directly. `applyCommand` now throws if `COMMAND_NEXT_DAY` is dispatched, and the day-rollover logic was moved into a private function called only by the `COMMAND_ADVANCE_SHIFT` handler. Prevents the derived-consequence-only guarantee from silently eroding as more UI code starts calling `dispatchCommand`.

**Content-derived data (POI `costShifts`, Endeavor phase IDs, `unlocksNodesOnComplete`) passed via command payload instead of looked up by the store.**
`src/engine/` may never import `src/content/`, but several command handlers (`COMMAND_MOVE_TO_POI`, `COMMAND_START_ENDEAVOR`, `COMMAND_ADVANCE_ENDEAVOR_PHASE`) need values that only exist in content JSON. Rather than weakening the decoupling rule, the caller — which does have content access — supplies those values as part of the payload. Documented in `web-implementation.md` §3 so Phase 6 (UI) follows the same pattern instead of reaching into content from the engine.

**`COMMAND_ADJUST_CURRENCY` auto-normalizes bronze→silver→gold on every adjustment; no negative-balance protection added.**
`game-design-spec.md` §5 states the 20:20 conversion rate but doesn't say whether it's applied automatically; auto-normalizing was inferred from `execution-plan.md` Phase 5 mentioning a "currency conversion boundaries (400 bronze = 1 gold)" store test. Negative-balance handling (e.g. blocking an unaffordable purchase) was deliberately left out — that's part of the economy-balance open design gap, not a structural/type concern, and inventing it now would preempt that spec.

**`worldClock.weather` added to `PlayerState` as a display-only field, no weather mechanic invented.**
`execution-plan.md`'s Phase 6 spec for `WorldClockHud` requires showing weather, but `PlayerState` had no weather field at all and `game-design-spec.md` §4 never defined its representation. Rather than skip the HUD element or invent a weather-change mechanic, added a minimal `Weather` enum (`CLEAR | RAIN | FOG | STORM`, mirroring the existing `Shift`/`Season` const-array pattern) purely so the field exists and can render. It starts at `CLEAR` and nothing currently changes it — no `CommandType` sets weather, since how/when it should change is undefined. Also promoted `Season` to the same named-const-array pattern as `Shift` while touching this code, for the same drift-prevention reason `Shift` was promoted earlier. The "nothing updates it" gap is now formalized as `game-design-spec.md`'s Open Design Gap #5, rather than only living in this log entry — so an implementer scanning gaps (not decisions) still finds it.

**`MinigameLauncherPayload.config`'s eventual shape (a discriminated union) logged as a formal open gap, not just fixed as `unknown` and left implicit.**
Changing `config: Record<string, any>` to `Record<string, unknown>` (see below) closes the immediate lint/strictness violation, but `unknown` is still a placeholder, not a real type — it says nothing about what a `DUEL` config vs. a `FISHING` config actually needs. Recorded in `game-design-spec.md`'s minigame-mechanics gap entry that once mechanics are specified, `config` should become `DuelConfig | LockpickingConfig | FishingConfig | DiceConfig` keyed off `type`, so the follow-up isn't lost between now and whenever that spec gets written.

**`config: Record<string, any>` changed to `Record<string, unknown>` in both `engine/types/index.ts` and `web-implementation.md` §4's code sample.**
`any` violated `CONTRIBUTING.md`'s "no any" rule (caught by `npm run lint`, not `tsc`, which doesn't flag it) — but it had been copied verbatim from `web-implementation.md` §4's own spec text in Phase 1, so fixing the code without fixing the doc would have made them diverge again. Both changed together, plus a comment in `index.ts` marking it a placeholder pending the minigame-mechanics spec.

**Component testing (`@testing-library/react` + `jsdom`) added to the tech stack as a standing rule, not a one-off.**
Phase 6 shipped six UI components with zero automated coverage — verified only via a manual Playwright/browser pass, which doesn't run on every future change the way `npm run test` does. Rather than re-litigate "does the DoD apply to UI" every phase, added the two packages to `CLAUDE.md`'s tech-stack boundary and wrote the rule directly into `CONTRIBUTING.md`: structure/behavior component tests (jsdom) are required alongside logic tests from now on; a full visual/real-browser pass (Playwright) is reserved for deliberate milestones via the new `ui-visual-check` skill, not routine per-phase work — screenshots are expensive and slow to be the default verification method for every small change.

**Dialogue branching logged as an open gap rather than left undiscovered.**
`Actor.initialDialogue` is one static string per Actor. The state needed to vary it (`activeEndeavors`, `unlockedClues`, `reputation`) already exists in `PlayerState`, which makes it tempting to wire up "if phase X, show line Y" ad hoc the next time an Actor needs more depth. Recorded as `game-design-spec.md` Open Design Gap #6 instead, since the actual mechanism (priority order between conditions, how much branching, authoring format) isn't specified and shouldn't be invented mid-feature.

**Engine UI components take content-derived data as props; only `App.tsx` imports `src/content/` directly.**
`web-implementation.md` §3 bars `src/engine/` from importing `src/content/`, but `WorldNavigationView` and `NodeInteractionCanvas` need settlement/district/POI/actor names and descriptions to render anything. Rather than weaken the boundary, `App.tsx` (outside `src/engine/`) does the content lookups and passes resolved data down as props — the same pattern already used for content-derived command payloads, applied to rendering.

**Actor-selection state (which NPC's dialogue is showing) kept as local React state, not added to `PlayerState`.**
It's view state — which panel of an already-open POI you're looking at — not something that needs to survive a reload or export. Adding it to `PlayerState`/`PlayerStateSchema` would have meant inventing a new persisted field with no gameplay meaning yet.

**"Leaving a POI" reuses `COMMAND_MOVE_TO_DISTRICT` instead of adding a new command.**
`COMMAND_MOVE_TO_DISTRICT` targeting the current `districtId` already clears `poiId` at zero shift cost, which is exactly "step back out to the district view." Adding a dedicated `COMMAND_LEAVE_POI` would have duplicated existing, already-tested behavior.

**`MinigameOverlay.tsx` added to the component directory tree; it wasn't in the original `web-implementation.md` §7 list.**
`execution-plan.md`'s Phase 6 section requires rendering the minigame modal overlay, but the five named components in §7 didn't include one for it. Added as its own file (full-screen modal, `activeMinigame`-driven, dispatches `COMMAND_RESOLVE_MINIGAME` with a hardcoded victory/defeat choice — no mechanic logic) rather than folding it into an existing component, and updated §7's file list to match.

**Testing moved from a dedicated end-phase to alongside implementation.**
Phase 3's command/store logic (shift rollover, currency conversion,
reputation clamping) shipped and was approved across two phases with
zero behavioral test coverage — only type-checking. Deferring all
tests to Phase 5 meant real logic bugs could sit undetected for
multiple approval cycles. Definition of Done now requires tests
alongside any new logic in the same phase it's introduced.

**CI Node version bumped from 20 to 24, matching local.**
jsdom 28's bundled undici (8.0.3+) requires `node:worker_threads.markAsUncloneable`,
added in Node v21.0.0. CI pinned to Node 20 caused all 6 component test files to
fail at worker startup (not a test failure — they never ran). Local Node 24 has
the API and was unaffected, which is why this wasn't caught until CI ran it.
Aligning versions everywhere going forward avoids this class of "works locally,
fails in CI" gap.

**Node version centralized into `.nvmrc`, rather than just fixing the CI number.**
Bumping `ci.yml`'s hardcoded `node-version: '24'` (above) fixed the immediate
failure but left two separately maintained copies of the same fact — nothing
stopping them from silently drifting apart again the next time either one
changes. Added `.nvmrc` (`24`) as the single source of truth: `ci.yml` now
reads `node-version-file: '.nvmrc'` instead of a hardcoded value, and
`package.json`'s `"engines": { "node": ">=24" }` makes `npm install` itself
warn locally on a mismatch. README points at `.nvmrc` so a human setting up
the repo sees the same requirement, not a fourth copy of the number.

**Currency borrow-down implemented as a single total-value reconstruction, not per-denomination borrowing.**
`COMMAND_ADJUST_CURRENCY` previously only carried up (bronze→silver→gold) and had no way to go the other direction, so a loss bigger than the bronze on hand would just leave a raw negative field. Rather than hand-write borrow logic per denomination (bronze short → break a silver → still short → break a gold → ...), the handler now converts the *entire* current balance to a single bronze-equivalent integer, applies the signed delta, clamps at 0 (the hard floor), and re-splits that one number back into gold/silver/bronze. Carry-up, borrow-down, and the negative-balance floor all fall out of the same three-line function instead of three separate code paths — and it's the same formula already used to compute `currenciesToBronzeEquivalent` for the dice wager ceiling, so there's one canonical definition of "how much money does the player have," not two.

**Dice minigame mechanic: 2d6, even/odd, 2x payout on win — chosen for simplicity/testability/transparent odds, not balance.**
Given four minigame types were completely unspecified, DICE was the one to resolve first because a pure coin-flip-shaped mechanic (parity of a 2d6 sum) has no skill component, no difficulty curve, and no hidden odds to get wrong — the player can mentally verify "even wins" is roughly 50/50 without trusting the implementation. `game-design-spec.md` §9 records this explicitly as a deliberately minimal first mechanic, not a template future minigames must copy.

**Mara Venn's `factionIds` corrected to `["faction_wagering_ring"]` only — `faction_city_watch` removed, not kept alongside it.**
The original starter content gave her City Watch affiliation as a placeholder; wiring her into an actual gambling loop this phase meant she needed to plausibly belong to the syndicate running it instead. Single-faction rather than dual (`factionIds` supports multiple) because there's no narrative reason yet for her to belong to both a law-enforcement faction and a gambling ring — adding both would have papered over the correction rather than making it. Her `title` ("City Watch Sergeant") and `description` were deliberately left untouched (out of scope for this correction), which now reads as narratively inconsistent with her faction — flagged for a follow-up content pass, not silently fixed.

**Player starts with a small currency purse (50 bronze-equivalent) instead of zero.**
Found via the browser verification pass, not requested in the spec: `initialPlayerState.currencies` was `{0,0,0}` from Phase 3, which made the new Gamble action permanently disabled on a fresh save — "Not enough coin" with no way to ever afford the 5-bronze minimum wager. A phase whose stated goal is "the first real playable loop" isn't actually playable if the loop is unreachable from the start. Picked a modest placeholder (`{gold:0, silver:2, bronze:10}`) rather than 0 or something large — explicitly flagged as a placeholder tied to the economy-balance open design gap, not a balanced number.

**Dice wager stays in sync with `activeMinigame` by re-dispatching `COMMAND_START_MINIGAME` on every stepper change, instead of adding a new command.**
The wager is chosen *after* the minigame launches (the player can adjust the stepper before throwing), but `COMMAND_RESOLVE_MINIGAME` needs `onSuccessCommands`/`onFailureCommands` to already contain the correct `COMMAND_ADJUST_CURRENCY` amount when it fires. Rather than add a `COMMAND_UPDATE_MINIGAME_CONFIG` or let `DiceGame` bypass the payload pattern and dispatch currency changes directly, `setWager` just re-sends the whole `COMMAND_START_MINIGAME` payload with the new wager baked into both command lists — `COMMAND_START_MINIGAME`'s handler already does a full overwrite of `activeMinigame`, so this needed zero store changes.

**Endeavor completion (`phase_confront_the_buyer`, which has no `nextPhaseOnSuccess`) marked via `COMMAND_UNLOCK_CLUE` with a dedicated clue ID, not a new command or state field.**
`activeEndeavors` entries have no `isComplete` flag, and this phase's instructions explicitly ruled out a schema change. `unlockedClues` was already exactly "a set of durable flags the player has reached" — reusing it for `clue_broadsheet_case_closed` cost nothing new and matches the session's running preference for reusing an existing primitive over inventing a command for a one-off need (see the `COMMAND_MOVE_TO_DISTRICT`-as-"leave POI" decision above).

**`NodeInteractionCanvas` gained a generic `actions?: NodeInteractionAction[]` prop instead of hardcoding Gamble/Pay-off-the-buyer into the component.**
Both actions are specific to one POI and one Endeavor phase — genuinely content-specific, not something `src/engine/components/` should know about by name. `App.tsx` builds the action list (which buttons, their labels, their `onClick` logic) and passes it down, consistent with every other content-derived prop the component already takes.

**`COMMAND_CANCEL_MINIGAME` added — a genuinely new command, unlike the clue-marker case below.**
Found via manual testing: a player who opens the Dice modal with too little to afford `MIN_WAGER` had no way to close it. `COMMAND_RESOLVE_MINIGAME` always applies `onSuccessCommands` or `onFailureCommands` — there was no existing command that clears `activeMinigame` without a win/lose consequence, and no existing primitive to repurpose for one (unlike "mark an endeavor complete," this need has no adjacent state that already means "leave without effect"). Kept minimal: no payload, clears `activeMinigame`, nothing else. `DiceGame`'s "Leave" button dispatches it and stays enabled even when "Throw" is disabled for insufficient funds.

**Reversed: endeavor completion no longer uses `COMMAND_UNLOCK_CLUE` as a marker — reverts the decision two entries above.**
On review, repurposing `unlockedClues` (meant for narrative discoveries) as a mechanical "already paid" flag was the wrong call — it solved a real problem (preventing repeat payment) by overloading a system that means something else. Removed the dispatch entirely rather than finding a different existing field to repurpose (state fields like `logHistory` or `unlockedNodes` would have had the same semantic-misuse problem, just relocated). "Pay off the buyer" now only dispatches its `COMMAND_ADJUST_CURRENCY` cost and stays visible/clickable for as long as `activeEndeavors[endeavorId].currentPhaseId === 'phase_confront_the_buyer'` — accepting that it's repeatable (each click cost real currency) as a deliberate simplification, the same category as the already-accepted no-anti-grinding reputation gap, rather than engineering real one-time-completion tracking without a schema change.

**Mara Venn's `title` and `description` updated to match her corrected faction, closing the gap flagged two entries above.**
Left as "City Watch Sergeant" / "A City Watch sergeant who..." when only `factionIds` was corrected, which just relocated the inconsistency from the faction field to the title/description instead of removing it. New title "Wagering Ring Regular"; description reframed around her being a trusted fixture at the tavern's back tables rather than an off-duty watch officer — keeps the "she hears things" Garrett-informant framing that made her useful as a source, drops the watch affiliation entirely.

**Fallen London, OGame, and BiteFight added as gameplay-systems inspirations — a new category, distinct from narrative/atmosphere/UI.**
`narrative-inspirations.md` previously covered narrative tone (§1), atmosphere (§2), and UI/interaction mechanics (§3) — nothing about repeatable-activity or progression *design*, even though the dice gambling loop just became the first real instance of that category with no reference to design against. Added as §4, explicitly marked as reference material "not yet adopted into concrete mechanics," not a spec — generalizing it into an actual system is deferred as `game-design-spec.md`'s Open Design Gap #9. Fallen London's entry includes a design-principles subsection sourced from a practitioner discussion (intfiction.org) on prototyping a similar Quality/Storylet system, kept alongside the game's own systems description since the principles are the more directly actionable part for future design work. Sensory palette renumbered from §4 to §5 to make room.

**Sound effects split into two trigger mechanisms — logic-driven (dice win/lose) and content-driven (`entrySoundAsset`) — rather than one unified system.**
The two cases genuinely have different owners: dice win/lose is a game-logic outcome with no content-JSON representation to hang a schema field off of, while District/POI entry is exactly the kind of per-node data `imageAsset` already models. Forcing both through a single mechanism would have meant either inventing fake content fields for the dice outcome or hardcoding a schema-driven lookup inside component logic that has nothing to do with content. `entrySoundAsset` (not `ambientSoundAsset`) was chosen deliberately: this phase is scoped to one-shot SFX triggered by a specific moment (arriving at a place), not looping ambience — naming it `ambientSoundAsset` would imply a persistent/looping sound bed that doesn't exist yet and would need different lifecycle handling (start on enter, stop on leave, no double-triggering) that's explicitly out of scope. Established now, in the same phase as the dice win/lose wiring, rather than deferred, because both need the same shared fail-silent utility — building that utility to serve only one caller would have been an artificial narrowing, and proving it against two independent trigger shapes (an outcome branch and a content field) in one pass is a stronger validation than doing them in separate phases. This also finally builds against the `audio/` folder that has sat referenced-but-unused in the directory blueprint since early in the project — the same category of "documented but never built" gap this session has closed before (e.g. `minigames/index.ts`, the content-integrity test).

**District's `entrySoundAsset` fires once on initial app mount, not from `onLeave` (the only place `COMMAND_MOVE_TO_DISTRICT` currently dispatches).**
The original plan wired it to `onLeave`, reasoning that's the only existing `COMMAND_MOVE_TO_DISTRICT` call site. On review this was wrong: `onLeave` fires when stepping out of a POI back into the *same* district the player never actually left — playing an "entering this district" sound there would misrepresent "leaving a building" as "arriving somewhere new." This was a semantic mismatch, not a technical limitation — nothing stopped the code from working, it just would have meant the wrong thing. A `useEffect` on mount against the currently-resolved district is the one place in the current single-district world that's honestly "the player has entered this district," and it keeps working unchanged once real district-to-district travel exists later (a future "move to district" action calls the same trigger function; the mount effect only needed a code comment flagging that its empty dependency array will need revisiting at that point, since `district` is a static import today). Dice win/lose and the POI entry sound (`onSelectPoi`, a real per-POI selection event) were not affected by this reconsideration — only the district-entry trigger point changed.

**`resetProgress` added as a store action (`usePlayerStore`), not an ad hoc `setState` call from `ManagementDrawer`.**
Mirrors `exportSave`/`importSave` exactly — both already live in the store as the sanctioned place for whole-state-replacement operations, and `resetProgress` is conceptually identical to `importSave` targeting a fixed value (`initialPlayerState`) instead of a parsed file. Keeping it in the store instead of the component means `ManagementDrawer` stays a thin consumer, consistent with every other store-native component in `src/engine/components/`. Dev-only gating (`import.meta.env.DEV`) and a two-click in-UI confirm step (not a native `window.confirm`, which is harder to test and less consistent with the game's own visual language) live in the component, since those are UI/UX concerns, not state-management ones.

**Referential-integrity checks in `content-integrity.test.ts` scoped to exactly three relationships (+ their reverses), not every reference-shaped field.**
`Actor.factionIds`, `POI.actorIds`/`Actor.poiId`, and `District.poiIds`/`POI.districtId` are checked. `controllingFactionId`, `factionInfluence` keys, `District.settlementId`, and `Endeavor.unlocksNodesOnComplete` are equally reference-shaped and equally checkable in principle, but were left out of this pass — extending referential-integrity checking to *every* reference field the schemas contain wasn't what was asked, and silently over-delivering would have made the actual scope of coverage less legible than stating it explicitly (which the test file's own comment now does). Extending further is a small, well-understood follow-up whenever it's actually needed, not a design problem to solve now.

## 2026-08-11

**Content loading in `App.tsx` routed through each schema's `.parse()` (`src/contentLoader.ts`'s `loadContent`) instead of consuming raw static `import`s directly — a root-cause fix, not a per-field patch.**
Found during the dialogue-branching phase: `DialogueChoiceSchema.commands` is declared `z.array(StateCommandSchema).default([])`, but that default is only ever applied when data is actually run through `.parse()`/`.safeParse()`. `App.tsx` loaded every content file (settlements, districts, POIs, actors, endeavors, dialogues) via plain `import x from "./content/....json"`, which returns the JSON exactly as authored — a field omitted in the raw file stays `undefined`, not `[]`. `content-integrity.test.ts` and `schemas.test.ts` both only ever exercise the *parsed* shape (they call `schema.safeParse(rawData)` themselves), so neither test file can distinguish "this field will be `[]` at runtime" from "this field will be `undefined` at runtime" — both look identical to a passing test. This shipped as a real bug: `dialogue_mara_venn.json`'s `choice_press_for_lead` omitted `commands`, and `COMMAND_SELECT_DIALOGUE_CHOICE`'s handler crashed (`commands is not iterable`) the first time a real player reached it, despite `npm run test` being fully green. Caught only by the manual browser reachability check (`docs/feature-workflow.md` Category A/E), not by any automated check.

The first fix (a defensive `commands ?? []` in the command handler) closed that one instance but was explicitly called out as treating a symptom — the same exposure exists for every other `.default(...)` field any content schema declares (`DialogueNodeSchema.choices`, `PoiSchema.costShifts`, `ActorSchema.factionIds`, and any future one), and patching each usage site as it's individually discovered doesn't scale and doesn't get found until something crashes in front of a player. Root-caused instead: `src/contentLoader.ts`'s `loadContent(schema, data, label)` runs every content import through `schema.safeParse`, throwing a clear, labeled error immediately on failure — matching `content-integrity.test.ts`'s existing strictness, now enforced in production too, not only at test time. Every component downstream of `App.tsx` can now assume any content-derived prop is the fully validated, defaulted shape its schema promises; the now-redundant `target?.costShifts ?? 0` fallback at the one live call site (`COMMAND_MOVE_TO_POI`'s payload) was simplified accordingly, since the only remaining reason for the `?:` there is "no matching POI found," not "the field might be missing."

Audited every content schema for other `.default(...)` fields as part of this fix: `Actor.factionIds` (default `[]`) and `Poi.costShifts` (default `0`) were the other two live instances; neither had a production consumer that would crash on `undefined` at the time (no code read `Actor.factionIds` outside tests, and `costShifts` already had a defensive `?? 0`), but both are now covered by the same loading-boundary fix regardless, so no per-field patch was needed for them. `DialogueRequirementSchema`'s `requires` field on a dialogue choice was checked separately and confirmed *not* exposed to this class of bug: it's `.optional()` with no `.default()`, so an omitted field is `undefined` whether parsed or raw — `evaluateDialogueRequirement`'s first line already treats `undefined` as "no requirement, always available," and that was true before this fix too.

Deliberately scoped to content-JSON loading only — `dispatchCommand`'s own input (commands `App.tsx`/`DialogueOverlay.tsx` build as plain TypeScript object literals) stays unvalidated at runtime, exactly as already scoped out in the dialogue-branching design doc and `web-implementation.md`'s `StateCommandSchema` note. Fixing that boundary is a separate, larger change touching every dispatch call site in the app, not a natural extension of this one.

**`npx tsc --noEmit` (bare) has been silently checking zero files all project long — fixed to `npx tsc -b --noEmit` everywhere it's used.**
Discovered by accident: `npm run build` (which runs `tsc -b && vite build`) failed on a genuine, pre-existing type error in `minigames.test.ts` that had never once surfaced across many phases of `npx tsc --noEmit` being run and reported clean, including in CI's "Type check" step. Root cause: `tsconfig.json` at the repo root only has `"references"` to `tsconfig.app.json`/`tsconfig.node.json`, no `"files"`/`"include"` of its own — bare `tsc` doesn't follow project references without the `-b` (build) flag, so it was compiling nothing and trivially "succeeding" every time. `npm run lint` didn't catch it either (no type-aware linting configured — confirmed by checking `eslint.config.js` for `parserOptions.project`, absent). This means the type error sat undetected through `tsc`, `lint`, and `test` alike — only a real production build surfaces this class of mistake. Fixed the command in `ci.yml`, `CONTRIBUTING.md`, and the `verify-phase` skill; fixed the one latent error it found (a payload cast in `minigames.test.ts`). This is exactly a category-D risk (`docs/feature-workflow.md`) — an environment/tooling assumption, true nowhere it was actually exercised until something finally exercised it.

## 2026-08-12

**`MinigameLauncherPayload.config` turned into a real discriminated union (`DiceConfig | DuelConfig` for the two resolved types, a loose bag for the two unresolved ones), rather than waiting for all four minigame types to be defined.**
Open Design Gap #1 originally framed this as an all-or-nothing move once `DUEL`/`LOCKPICKING`/`FISHING` were all specified. Doing it now, with only DICE+DUEL resolved, was still correct: TypeScript's discriminated unions work member-by-member, so `LOCKPICKING`/`FISHING` can keep their `Record<string, unknown>` branch unchanged until their own specs land, with zero disruption to DICE/DUEL's typed branches when that happens. `DistanceState` lives in and is re-exported from `duel.ts` (its natural home, mirroring `dice.ts` owning `RandomSource`/`DiceRollResult`) rather than being duplicated in `types/index.ts`.

**`DuelContext` bundles `player`/`opponent`/`distance`/`lastPlayerAction`/`playerReputation` as one object instead of positional parameters — a deliberate future-proofing choice, not incidental.**
The brief for this phase explicitly asked for this shape so that a later addition (equipped weapon informing poise or opponent AI, `game-design-spec.md` Open Design Gap #11) becomes a context-field addition, not a signature change to `evaluateDuelTurn`/`chooseOpponentAction`. `playerReputation` mirrors `PlayerState.reputation`'s exact shape rather than a narrower "just the wagering-ring number" field, so a future action could read a different faction/actor's reputation without widening the type again.

**Taunt's reputation check hardcodes `faction_wagering_ring` inside `duel.ts`, rather than making the target faction part of `DuelConfig`.**
This is explicitly the one worked example the brief asked for ("this first duel only... not a general taunt system"), so generalizing it into an authorable config field would have built a system nobody asked for yet and no second instance to validate the shape against. Revisit if/when a second duel wants a Taunt tied to a different faction.

**Guard-break: a combatant whose poise is already 0 takes bonus energy damage (`GUARD_BREAK_BONUS_DAMAGE`) from a landed Thrust/Dirty Trick — added during plan review, not in the original brief.**
The original brief left poise reaching 0 as purely informational (feeding `chooseOpponentAction`'s heuristics and the UI only). On review, poise hitting 0 with no mechanical consequence at all felt like a missing payoff for a whole stat track — an open guard being a real opening is a natural, minimal addition, not scope creep, since it only fires on a state (poise 0) the original design already tracked. Evaluated off the *pre-turn* poise value specifically so a Dirty Trick's own poise-drain can't retroactively bonus its own damage in the same turn, and never applies to riposte counter-damage (a `PARRY_RIPOSTE` effect, not a `THRUST`/`DIRTY_TRICK` hit). Flagged as a placeholder constant (15) alongside every other duel number, same as `dice.ts`'s wager constants.

**Mutual-knockout tie-break resolves as `PLAYER_DEFEAT`, and `chooseOpponentAction` never selects `TAUNT` — both are placeholder/first-mechanic choices, not considered design.**
Neither was specified in the brief. Checking `player.energy <= 0` before `opponent.energy <= 0` was an arbitrary pick to make the outcome function total (something has to win a same-turn double-KO); Taunt only ever being player-initiated follows directly from its reputation check being meaningful only for the player's own standing, not a general mechanic the opponent AI should reach for.

**Rapier Duel shipped engine-only this phase — no POI/NPC dispatches `COMMAND_START_MINIGAME` with `type: "DUEL"` yet.**
The dice minigame's own history (`docs/features/feature_dice_minigame.md`) shipped fully built and tested but unreachable from a fresh save, caught only by manual testing after the fact. Rather than risk repeating that, or invent an opponent NPC/POI not asked for, this was made an explicit, logged decision instead: per `feature-workflow.md` §2 stage 3, content-wiring is its own later Content/Adventure-spec phase, sequenced after the engine capability it depends on. `docs/features/feature_rapier_duel.md`'s Reachability section names this directly so it reads as a decision, not an oversight.

**`initialPlayerState.inventory` seeded with `item_rapier` ×1 — the first non-empty starting inventory, flavor-only this phase.**
Existing tests (`commands.test.ts`'s `COMMAND_ADD_ITEM` test, `playerStore.test.ts`'s initial-state shape assertion) assumed an empty starting inventory; updated in place rather than left broken, since an empty inventory was never a documented invariant, just an accident of `inventory` never having a starter item before. Doesn't gate Thrust or any other duel action, and poise isn't derived from it yet — logged as `game-design-spec.md` Open Design Gap #11 so the intended future connection (a better rapier raising poise) isn't lost.

**Item made a real content type (`ItemSchema`, `src/content/items/`), not a special case bolted onto `PlayerState.inventory`.**
`item_rapier` existed only as a bare string id with no display data, so the inventory tab showed the raw id. Rather than hardcode a name/description/image lookup table somewhere ad hoc, Item follows the exact same `BaseNodeFieldsSchema.extend(...)` + `loadContent` + content-integrity-glob pattern every other entity already uses — Settlement/District/POI/Actor/Faction/Endeavor/Dialogue all work this way, and an Item is not meaningfully different from those in terms of "how does content get validated and loaded," only in what fields it needs.

**`ItemSchema.imageAsset` overridden to be required, unlike `BaseNodeFieldsSchema`'s optional default.**
Every other content type can go without an image (a POI or Actor with no art is still fully functional). An inventory item without a visible representation defeats the purpose of adding Items at all — the user's request was specifically for a visible name/description/image, not a data record. Every other field on `ItemSchema` (`id`, `name`, `description`, `isUnlocked`) is inherited unchanged.

**`stackable: boolean` added to the Item schema now, with zero enforcement anywhere.**
The user asked for the stackable-vs-unique distinction to exist in the data model before more items get authored, but nothing today would ever add a second copy of any item — there's no second rapier, no crafting, no loot drop. Building enforcement logic (reject/cap a duplicate unique item) ahead of a real case to test it against would be guessing at a policy nobody's asked for yet (what should happen — silently ignore the second copy? Replace it? Error?). Logged as `game-design-spec.md` Open Design Gap #12 instead, alongside the closely related "no equipped-item concept" gap from #11 — both need their own spec once a second item (or the rapier-swapping feature) actually motivates one.

**Asset paths resolved against `import.meta.env.BASE_URL` at the point they become a real `src`/`Audio()` call, via a new shared `resolveAssetUrl` helper — not by rewriting every content file's `imageAsset`/`entrySoundAsset` to be base-aware.**
Found by adding the first real asset file (`item_rapier`'s artwork): `vite.config.ts` sets `base: '/broadsheet-rapier/'` for GitHub Pages, but every content-authored path is a literal root-relative string (`/content/assets/...`), and nothing resolved it against the configured base — so it 404'd under both `npm run dev` and the production build. This was invisible for the entire project so far because every image asset was already showing the MISSING placeholder for an unrelated reason (no file had ever existed), so a wrong URL and a genuinely missing file looked identical. Fixed at the two chokepoints where a path becomes an actual request — `AssetFallback.tsx` (images/audio-with-controls) and `playSound.ts` (fire-and-forget SFX) — rather than teaching every content author to bake `BASE_URL` into their JSON, which would also break the moment the base path ever changes again. The MISSING placeholder's label still shows the original authored path, not the resolved URL, so content authors keep debugging against what they actually wrote.

**`npm run lint` added as its own explicit step in `CONTRIBUTING.md`'s Definition of Done and the `verify-phase` skill, not left implicit under "CI covers it."**
CI failed on commit `a50473b` (`duel.ts`'s `player`/`opponent` declared `let` but only ever mutated via property assignment, never reassigned — `prefer-const`), even though that phase's own report showed a clean `tsc -b --noEmit` and a fully green `npm run test`. Root cause: neither `CONTRIBUTING.md`'s Definition of Done nor the `verify-phase` skill's checklist ever instructed running `npm run lint` locally — the skill's old step 6 only *mentioned* that CI runs lint, which reads as reassurance ("already covered") rather than an instruction to actually run it before declaring a phase done. `tsc` and ESLint check genuinely different things (this exact error isn't a type error), so passing one is no signal about the other. Both docs now list lint as its own required step, matching CI's actual order (type check → lint → test) exactly, so "phase done" locally means the same three checks CI will run, not two of three.

**`ManagementDrawer` takes an `items: Record<string, ItemDisplayData>` prop, not an `Item` (content type) import.**
`src/engine/` may never import `src/content/` directly (`web-implementation.md` §3) — `App.tsx` resolves the full `Item` content and maps it down to the three fields the component actually renders (`name`, `description`, `imageAsset`), the same content-derived-props pattern already used for `endeavorTitles` and `NodeInteractionCanvas`'s `actors` prop. `ItemDisplayData` is a plain interface owned by `ManagementDrawer.tsx` itself, not a re-export of the schema-inferred `Item` type.
